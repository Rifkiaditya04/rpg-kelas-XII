# 🔴 Temuan penting #1 — AC-003

`BI12-W1-AC-003` diberi:

```text
question_type: evidence_matching
```

tetapi sebenarnya datanya berbentuk:

```text
A. pasangan yang benar
B. pasangan yang benar
C. pasangan yang benar
D. pasangan yang salah

answer = A
```

Sementara renderer saat ini hanya melakukan pemilihan opsi biasa. Source renderer aktual menunjukkan `evidence_matching` memang ada dalam `SUPPORTED_TYPES`, tetapi tidak mempunyai interaction branch khusus; `render()` tetap membuat tombol pilihan biasa.

Jadi:

**Evidence:** pasangan A memang benar.
**Implementation:** belum ada mekanik matching sungguhan.
**Interpretation:** soal tersebut memakai nama "matching", tetapi pengalaman bermainnya sebenarnya MCQ.

### Keputusan

**Jangan masukkan ke Golden Dataset.**

Nanti kita ubah menjadi **MCQ evidence-based** atau kita benar-benar membuat mekanik matching.

Untuk menjaga scope dan kecepatan proyek, saya merekomendasikan **ubah menjadi MCQ** terlebih dahulu.

# 🔴 Temuan penting #2 — AC-004

`BI12-W1-AC-004` diberi:

```text
question_type: ordering
```

tetapi bentuk datanya:

```text
A. Tempat → Perihal → Alamat → Salam
B. ...
C. ...
D. ...
```

dan `answer` hanya berupa satu string.

Renderer juga tidak melakukan drag/drop atau penyusunan urutan. Ia hanya mengacak opsi lalu meminta pengguna memilih satu.

Jadi ini sebenarnya **MCQ tentang urutan**, bukan **ordering interaction**.

### Keputusan

Kita **tidak akan memaksakan label `ordering`** hanya agar dataset terlihat lebih bervariasi.

Untuk batch ini saya akan mengubahnya menjadi MCQ.

True ordering mechanic bisa kita bangun nanti apabila memang memberikan manfaat pedagogis yang cukup besar.

## Interpretation

Ini kemajuan penting karena kita baru saja membuktikan prinsip yang akan sangat penting ketika jumlah soal nanti mencapai ratusan atau ribuan:

> **Nama interaction type tidak boleh lebih maju daripada kemampuan game sebenarnya.**

Daripada kita memaksa:

```text
ordering
```

padahal belum ada ordering UI, kita memilih:

```text
MCQ
+
structure_check
```

Begitu nanti kita benar-benar membangun mekanik drag-and-drop, barulah kita bisa memperkenalkan `ordering` sebagai interaction type yang nyata.

Hal yang sama berlaku untuk `evidence_matching`.

Ini membuat **data → renderer → gameplay** tetap sinkron.
